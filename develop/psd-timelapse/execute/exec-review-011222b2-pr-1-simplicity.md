# Simplicity Review: pr-1 — Shared Client Contracts & Taxonomy

## [Simplicity]
### Issue 1 -- Severity: suggestion
- **File**: `packages/client/tests/contract_client_protocol.test.ts:1-280`
- **Description**: The protocol conformance test contains five full mock class declarations plus one aggregate mock (~240 lines) for a test file that ends with only 2 assertions. Each mock implements every interface method with trivial `{}` or hardcoded returns. This adds significant maintenance burden for what amounts to a TypeScript compilation smoke test — if the types compile, the mocks are trivially correct. The entire test structure mirrors the five-subsystem + aggregate split from the design doc, which compounds the bloat when any protocol gains a new parameter, every mock must be updated in lockstep despite none being exercised meaningfully.
- **Suggestion**: Replace with a lightweight type-level conformance check. For example, use an inline object literal per interface (`const transport: IClientTransportProtocol = { get: async () => {}, post: async () => {} };`) or remove the file entirely and rely on the existing schema contract test + normal typecheck (`npx tsc --noEmit`) to catch surface-level regressions. If keeping conformance tests is desired for future reference, collapse all five mocks into a single `it("all interfaces compile", () => {})` using inline type assertions rather than separate class declarations.
- **Status**: open

### Issue 2 -- Severity: suggestion
- **File**: `packages/shared/src/client/taxonomy_client_error.ts:56-72`
- **Description**: `NetworkConnectionError` and `ServerStreamError` are two near-identical subclasses whose constructors differ by exactly three characters (`"NETWORK_CONNECTION_ERROR"` vs `"STREAM_ERROR"`, `"NetworkConnectionError"` vs `"ServerStreamError"`). Neither is imported anywhere outside this file — confirmed by grep across the entire packages directory yielding zero non-test usages. They add subclass boilerplate (constructor forwarding, `this.name` assignment, prototype chain) with no behavioral difference from constructing `new ApiTransportError(...)` directly with the matching code. The current codebase has zero consumers of these classes.
- **Suggestion**: Remove both subclasses and their corresponding tests (`unit_client_error.test.ts` lines 99–140) until a real consumer requires them. A single `ApiTransportError` with an explicit `code` field covers the same ground. Deferring aligns with the prior-review note that "consumers arrive in PR 2 capabilities."
- **Status**: open

### Issue 3 -- Severity: nit
- **File**: `packages/shared/src/client/utility_client_url.ts:36-53`
- **Description**: `appendQueryParams` accepts `Record<string, string | number | boolean | undefined>` but immediately calls `String(value)` on every entry, discarding the numeric and boolean branch information at runtime. The union type gives a false impression that numbers and booleans are handled specially, when they are simply coerced to strings anyway. Additionally, `buildApiUrl` (lines 24–33) still hand-concatenates base + route strings with trailing-slash stripping and leading-slash injection — the same deferred simplicity nit from the prior merged review that was marked "deferred to PR 2 if simpler" and has not been addressed.
- **Suggestion**: Simplify `appendQueryParams` to accept `Record<string, string>` since all values are stringified anyway. For `buildApiUrl`, replace the manual string-join logic with `new URL(resolved, base).href` (or `.toString()` on the pathname + search) for clarity and fewer edge cases around double slashes.
- **Status**: open

### Issue 4 -- Severity: nit
- **File**: `packages/shared/src/client/utility_client_parser.ts:18-67`
- **Description**: `parseSseChunk` manually implements a full SSE frame parser with regex-based blank-line splitting, per-line prefix matching, comment/retry filtering, and data-line accumulation (~50 lines). While functionally correct and well-tested (21 unit tests), SSE parsing is production-grade complexity for utilities that currently have **zero non-test consumers** anywhere in the codebase. The line-by-line state machine handles edge cases (trimmed colons, multiple data lines) that no caller exercises today.
- **Suggestion**: No immediate change required given the test coverage, but flag this as debt to revisit when the first SSE consumer lands in PR 2+. At that point, decide whether the existing parser is sufficient or whether a simpler event-target-based approach would reduce the implementation footprint. The current breadth is defensible as forward-compatibility work, but the cost is ~50 lines of parser logic with no active consumer validating the investment.
- **Status**: open

### Issue 5 -- Severity: suggestion
- **File**: `packages/shared/src/client/taxonomy_client_vo.ts`
- **Description**: Five exported VO interfaces are field-for-field identical to their corresponding `*ResponsePayload` interfaces in `taxonomy_client_response.ts`. A programmatic field comparison confirms byte-identical field sets for the following pairs: `SystemHealthVO` ↔ `HealthResponsePayload`, `SystemConfigVO` ↔ `ConfigResponsePayload`, `ProgressSnapshotVO` ↔ `ProgressResponsePayload`, `RenderOutputMetaVO` ↔ `OutputMetaResponsePayload`, and `LayerMetadataVO` ↔ `LayerPayload`. Together with `RunIdVO` (0 references anywhere), `LayerMetadataVO` (0 references outside definition), and `LayerClassificationType` (only referenced by `LayerMetadataVO` which itself is unused), these add ~40 lines of parallel type definitions with zero production consumers outside test mocks. The previous merged review flagged this as Issue 1 of [Simplicity] with status "deferred"; the round-2 fix updated `RenderOutputMetaVO.state` to `string` (aligning it with `OutputMetaResponsePayload.state`) rather than removing the duplicate. This is a direct contradiction — round 2 both affirmed the duplication exists and added more surface to it.
- **Suggestion**: Reconsider deferring removal. Options: (a) collapse `SystemHealthVO`, `SystemConfigVO`, `ProgressSnapshotVO`, `RenderOutputMetaVO`, `LayerMetadataVO`, `RunIdVO`, and `LayerClassificationType` until a real surface consumer needs a distinct shape; have `IClientAggregate` return the `*Payload` types directly (PR 4 will need to add translation anyway if VO shapes diverge). (b) If the design doc §4.3 insists on domain VOs distinct from wire payloads, give at least one VO a distinguishing field or comment explaining why it exists separately from its identical Payload twin. As currently written, every VO either duplicates a Payload or is unreferenced.
- **Status**: open
